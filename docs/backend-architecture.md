# وثيقة معمارية الخادم والمنظومة الخلفية | Backend Architecture — مشروع عصبون (osboon)

## 1. مقدمة والهدف المعماري (Introduction & Architectural Objective)

تهدف هذه الوثيقة إلى تحديد وتوثيق **معمارية النظام الخلفي (Backend Architecture)** لمشروع **عصبون (osboon)** على المستوى المنطقي والهيكلي، استنادًا إلى نموذج البيانات المنطقي (`docs/logical-data-model.md`) ونموذج الوصول وأمن البيانات (`docs/data-access-security-model.md`) وكافة المرجعيات السابقة للنظام.

تحدد هذه الوثيقة:
- الطوبولوجيا العامة للنظام وتوزيع المسؤوليات بين العميل (Client) والخادم (Backend) وقاعدة البيانات (Database) والتخزين (Storage).
- الطبقات المنطقية للـ Backend وحدود العزل بينها لمنع تداخل المسؤوليات.
- مواضع فرض قواعد الأمان وصلاحيات الوصول (Security Enforcement Boundaries).
- المعمارية الداعمة لنمط العمل المحلي أولاً (**Local-First**) والتزامن السحابي (**Cloud Sync**).
- المسارات والتدفقات المعمارية الأساسية للعمليات الحيوية (المصادقة، مساحات العمل، المكتبة العامة، والمراجعة التعاونية).

> **حدود النطاق:** يقتصر هذا المستند على **التصميم المعماري المنطقي وتوزيع المكونات**، ولا يتضمن أي تفاصيل تنفيذية تقنية مثل كتابة أكواد Dart/Drift، أو سكربتات SQL/Migrations، أو أكواد TypeScript للـ Edge Functions، أو سياسات RLS تفصيلية، أو تفاصيل حزمة التسليم (Handoff) المخصصة للمرحلة اللاحقة (#22).

## 2. الطوبولوجيا العامة وتوزيع المنظومة (System Topology)

تعتمد المنظومة بنية موزعة تجمع بين تطبيق عميل محلي يعتمد فلسفة **Local-First** وخادم سحابي مبني بالكامل على منظومة **Supabase**:

```text
┌──────────────────────────────────────────────────────────────────────────────────┐
│                             Client Tier (Flutter App)                            │
│  ┌───────────────────────┐   ┌────────────────────────┐   ┌───────────────────┐  │
│  │   UI & Presentation   │   │  Local DB Sync (Drift) │   │  supabase_flutter │  │
│  └───────────────────────┘   └────────────────────────┘   └─────────┬─────────┘  │
└─────────────────────────────────────────────────────────────────────┼────────────┘
                                                                      │ HTTPS / WSS
┌─────────────────────────────────────────────────────────────────────▼────────────┐
│                             Backend Tier (Supabase)                              │
│                                                                                  │
│   ┌──────────────────────────────────────────────────────────────────────────┐   │
│   │                         API & Ingress Gateway                            │   │
│   │         (Supabase API Gateway / Kong - JWT Verification & Routing)       │   │
│   └───────────────┬───────────────────────────┬──────────────────────────────┘   │
│                   │                           │                                  │
│      ┌────────────▼────────────┐  ┌───────────▼────────────┐                     │
│      │   PostgREST Data API    │  │  Custom App Services   │                     │
│      │ (Declarative CRUD & Sync│  │    (Edge Functions)    │                     │
│      └────────────┬────────────┘  └───────────┬────────────┘                     │
│                   │                           │                                  │
│   ┌───────────────▼───────────────────────────▼──────────────────────────────┐   │
│   │                       PostgreSQL Database Core                           │   │
│   │    - Relational Storage (Logical Entities & Metadata)                    │   │
│   │    - Security Enforcement Boundary (Row Level Security - RLS)            │   │
│   │    - Transactional Invariants & State Validations                        │   │
│   └───────────────────────────────────────────┬──────────────────────────────┘   │
│                                               │ References                       │
│   ┌───────────────────────────────────────────▼──────────────────────────────┐   │
│   │                      Supabase Object Storage                             │   │
│   │    - Shared Content Assets (.md, .json) & Compiled Manifests             │   │
│   │    - Private Workspace Overrides & Proposal Uploads                      │   │
│   └──────────────────────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### توصيف الطبقات الرئيسية (Tiers):
1. **Client Tier (Flutter + Drift):**
   - يدير واجهة المستخدم والتفاعل المحلي الفوري دون تأخير شبكي.
   - يعتمد على **Drift** (مكتبة SQLite لـ Flutter) كمستودع محلي أولي للبيانات؛ حيث تُخزن المقررات، والدروس، والبطاقات التعليمية محليًا.
   - يتواصل مع الخادم عبر المكتبة الرسمية `supabase_flutter` لإجراء المصادقة، وجلب الأصول، ومزامنة المسودات السحابية.
2. **Backend Tier (Supabase Infrastructure):**
   - **Supabase Auth:** المزود المركزي للتحقق من الهوية وإصدار وإدارة جلسات المستخدمين ورموز المصادقة (JWT).
   - **PostgREST (Data API):** طبقة وسيطة مؤتمتة لتحويل طلبات الـ HTTP إلى استعلامات SQL مقيدة بصلاحيات الـ JWT المفحوصة في قاعدة البيانات.
   - **Edge Functions (Domain Orchestrator):** خدمات سحابية مخصصة للعمليات المعقدة متعددة الأطراف، مثل اختيار المراجعين عشوائيًا، وتجميع المانيفست، وتوليد الإصدارات المعتمدة.
   - **PostgreSQL Database:** المستودع العلائقي المركزي ومصدر الحقيقة الثابت لكافة الكيانات، والبيانات الوصفية، والروابط، وسجلات الحالات.
   - **Supabase Storage:** مستودع الكائنات الثابتة (Object Storage) لحفظ وتوزيع ملفات المحتوى التعليمي الكبيرة والمضغوطة (`.md`, `.json`, `manifest.json`).

## 3. المكونات والطبقات المنطقية للـ Backend (Backend Logical Layers)

لضمان عزل المسؤوليات وعدم تداخل المنطق الإجرائي، يُقسم الـ Backend إلى خمس طبقات منطقية واضحة:

```text
[1. Authentication & Identity Layer] ──► Supabase Auth
                   │
[2. Ingress & Routing Layer]         ──► API Gateway / PostgREST / Functions Dispatcher
                   │
[3. Domain Orchestration Layer]      ──► Edge Functions (Workflows & Complex Logic)
                   │
[4. Security & Enforcement Boundary] ──► PostgreSQL RLS Policies & Storage Access Rules
                   │
[5. Persistence & Storage Layer]     ──► PostgreSQL Tables & Supabase Storage Buckets
```

### 1. طبقة الهوية والمصادقة (Authentication & Identity Layer)
- **المسؤولية:** التحقق من صلاحية المستخدم، وإصدار الـ JWT المحمل بمعرف الهوية `Identity.id`، وإدارة تجديد الجلسات.
- **الحدود:** لا تتدخل في الصلاحيات الوظيفية أو التمييز بين حسابات الطلاب والمعلمين؛ دورها ينتهي عند إثبات صحة الهوية الرقمية للمستخدم.

### 2. طبقة البوابة والواجهات (Ingress & Routing Layer)
- **المسؤولية:** استقبال الطلبات القادمة من `supabase_flutter`، وتمرير الـ JWT إلى قاعدة البيانات، وفصل الطلبات المباشرة (عبر PostgREST) عن العمليات الإجرائية الموجهة إلى الـ Edge Functions.
- **الحدود:** لا تحتوي على منطق عمل (Business Logic)؛ وظيفتها التوجيه والتحقق الشكلي من الطلبات.

### 3. طبقة التنسيق ومنطق العمليات (Domain Orchestration Layer)
- **المسؤولية:** تنفيذ مسارات العمل متعددة الخطوات التي تتجاوز مجرد القراءة والكتابة البسيطة، وتشمل:
  - إدارة مسار دعوات المراجعة وتعيين المراجعين وفق خوارزميات النزاهة.
  - تقييم اكتمال النصاب للمقترح وإصدار قرار الاعتماد (`Approved Update`).
  - معالجة وإشهار الإصدار الجديد (`Version Promotion`) وتجميع ملف المانيفست الموحد.
  - تنفيذ عمليات التطهير الفيزيائي المؤجل للمسودات (`Deferred Purge`).
- **الحدود:** لا تخزن بيانات مستقلة بذاتها؛ تعتمد بالكامل على قاعدة البيانات والتخزين وتعمل بمبدأ عدم حفظ الحالة (Stateless).

### 4. طبقة فرض الأمان والسياسات (Security & Enforcement Boundary)
- **المسؤولية:** التطبيق الحاسم لقواعد `Data Access & Security Model`، بحيث تُطبق سياسات العزل والأمان داخل محرك قاعدة البيانات ومستودع التخزين مباشرة:
  - منع الوصول لأي سجل إلا عبر التحقق من سلسلة الملكية (`Account` ← `Identity`).
  - عزل بيانات الـ `Workspace*` الخاصة لكل حساب.
  - فرض ثبات كيانات المكتبة العامة والإصدارات المعتمدة (`Immutability`).
- **الحدود:** هي خط الدفاع النهائي والأول؛ لا يمكن لأي طبقة عليا (سواء واجهات API أو Edge Functions) تجاوز هذه الحدود إلا عبر هويات وصول خدمية مقيدة وموثقة بدقة.

### 5. طبقة التخزين والاستدامة (Persistence & Storage Layer)
- **المسؤولية:**
  - **قاعدة البيانات العلائقية:** استدامة الكيانات الـ 23 المحددة في `Logical Data Model`، وضمان التكامل المرجعي والقيود الهيكلية.
  - **مستودع الكائنات (Object Storage):** استضافة الملفات التعليمية المصدرية (`.md`)، والملفات المهيكلة (`.json`)، وملفات المانيفست الشاملة للإصدارات (`manifest.json`).
- **الحدود:** تفصل قاعدة البيانات بين الـ Metadata ومسارات التخزين (`storage_path`) والـ `checksum`، بينما يقتصر الـ Object Storage على استضافة المحتوى الثابت والمضغوط دون معرفة بالعلاقات الهرمية.

## 4. حدود المكونات ومنع تداخل المسؤوليات (Component Separation of Concerns)

| المكون | ما يقع داخل مسؤوليته حصرًا | ما يُحظر عليه القيام به (خارج حدوده) |
|---|---|---|
| **تطبيق العميل (Flutter + Drift)** | - إدارة التخزين المحلي، وحالات الواجهة، وعمليات القراءة والدراسة دون اتصال.<br>- إشتقاق حالة المزامنة `sync_status` بمقارنة الإصدار المثبت بالإصدار العام.<br>- تخزين التعديلات المؤقتة محليًا قبل المزامنة. | - محاولة فرض سياسات أمان عليا أو اعتبار التحقق من جهة العميل كافيًا.<br>- كتابة محتوى مباشر في جداول المكتبة العامة.<br>- تنفيذ عمليات اعتماد المقترحات وتوليد الإصدارات. |
| **قاعدة البيانات (PostgreSQL Core)** | - فرض القيود الهيكلية والفريدة ومطابقة الشروط (`Constraints`).<br>- فرض أمن السجلات وعزل المستأجرين عبر RLS.<br>- إدارة العلاقات المفاهيمية وسجلات التغيير والحالات. | - تخزين نصوص الملفات التعليمية الكبيرة أو حزم الاختبارات مباشرة داخل حقول الجداول.<br>- تنفيذ عمليات اتصال خارجي أو خوارزميات معقدة خارج نطاق البيانات العلائقية. |
| **مستودع الكائنات (Object Storage)** | - تخزين محتويات الملفات المشتركة والخاصة وملفات المانيفست المجمعة بصيغة خام.<br>- التحقق من صحة الملفات عبر مطابقة الـ `checksum`.<br>- توفير وصول سريع للقراءة للملفات المشتركة عبر شبكات التوزيع. | - استنتاج أو تتبع البنية الهرمية للمقرر (الوحدات والدروس).<br>- السماح برفع أو قراءة ملف لا يرتبط بسجل شرعي مسجل في قاعدة البيانات. |
| **خدمات العمليات (Edge Functions)** | - تنسيق العمليات الحسابية والتنظيمية لمسار المراجعة والاعتماد.<br>- سحب الملفات المعتمدة، وبناء ملف المانيفست، وإنشاء سجل الإصدار في معاملة مجمعة.<br>- إدارة المهام المجدولة (مثل إنهاء صلاحية الدعوات المتأخرة). | - تكرار كود الاستعلامات البسيطة التي يمكن لـ PostgREST تنفيذها بأمان وكفاءة.<br>- تجاوز قواعد الأمان وعزل البيانات بدون مبرر خدمي صريح. |

## 5. المسارات والتدفقات المعمارية الأساسية (Core Architectural Flows)

---

### أولاً: مسار الهوية والحساب النشط (Identity & Active Account Flow)

```text
[Flutter Client]                  [Supabase Auth]              [PostgreSQL (RLS)]
       │                                 │                             │
       │── 1. Authenticate (Login) ─────►│                             │
       │◄── 2. Return Session + JWT ─────│                             │
       │      (Contains identity_id)     │                             │
       │                                                               │
       │── 3. Select Account Context ─────────────────────────────────►│
       │      (StudentAccount vs TeacherAccount linked to identity_id) │
       │                                                               │
       │── 4. Subsequent Data Requests (with Account Context) ────────►│
       │      (Evaluates RLS via Current Account & Identity Chain)     │
```

- يدخل المستخدم عبر Supabase Auth ويستلم الرمز الأمني المشفر (JWT) الحامل لـ `Identity.id`.
- يستعلم العميل عن الحسابات الوظيفية التابعة لهويته (`StudentAccount` أو `TeacherAccount`).
- يحدد المستخدم السياق النشط في التطبيق؛ وتمرر الطلبات اللاحقة معرف الحساب النشط ليُطابق ضمن سلسلة الملكية الصارمة (`Account.id = Current_Account` و `Account.identity_id = Identity.id`) لفتح مساحات العمل التابعة له فقط.

---

### ثانياً: مسار مساحات العمل والمزامنة السحابية (Workspace & Cloud Sync Flow)

يطبق هذا المسار معمارية **Local-First** مع مزامنة سحابية اختيارية للنسخ الاحتياطية والتعديلات:

```text
[Local Drift DB]          [Flutter Client]           [PostgREST / API]        [Supabase Storage]
       │                         │                           │                         │
       │── 1. Local Edit/Read ──►│                           │                         │
       │   (Instant, Offline)    │                           │                         │
       │                         │                           │                         │
       │◄── 2. Save Locally ─────│                           │                         │
       │                         │                           │                         │
       │   [When Cloud Sync Triggered]:                      │                         │
       │                         │── 3. Upload File Payload ─┼────────────────────────►│
       │                         │◄── 4. Return storage_path ┼─────────────────────────│
       │                         │                           │                         │
       │                         │── 5. Upsert Workspace* ──►│                         │
       │                         │   (Course/Lesson/Content) │                         │
       │                         │◄── 6. Confirm Sync ───────│                         │
```

1. **العمليات اليومية:** تتم القراءة والتعديل محليًا في قاعدة بيانات **Drift** على جهاز المستخدم بسرعة فائقة ودون الحاجة لاتصال بالإنترنت.
2. **المزامنة السحابية (Cloud Sync):** عند تفعيل المزامنة أو الاستعداد لتقديم مقترح:
   - يرفع التطبيق ملف المحتوى المعدل إلى مسار التخزين الخاص في `Supabase Storage` مستخرجًا الـ `storage_path` والـ `checksum`.
   - يسجل التطبيق بيانات التجاوز في كيان `WorkspaceContentItem` (مربوطًا بـ `version_lesson_id` لدروس المكتبة كنسخة خاصة `Private Copy`، أو `workspace_lesson_id` للدروس المحلية).
   - يتم التعامل مع كيانات `Workspace*` على السحابة كطبقة مزامنة مستودعية وليس كبديل لقاعدة البيانات المحلية.

### ثالثاً: مسار القراءة المرجعية من المكتبة العامة (Public Library Reference Reading)

```text
[Flutter Client]              [PostgREST / DB]              [Supabase Storage / CDN]
       │                              │                                │
       │── 1. Browse / Search ───────►│                                │
       │   (LibraryCourse & Version)  │                                │
       │◄── 2. Return Catalog Metadata│                                │
       │                              │                                │
       │── 3. Adopt Course (Pin vX) ─►│                                │
       │   (Creates WorkspaceCourseReference)                          │
       │                              │                                │
       │── 4. Fetch Version Manifest ─┴───────────────────────────────►│
       │◄── 5. Stream manifest.json & Download Shared Assets ──────────│
       │                                                               │
[Saves to Local Drift DB] ◄── Cached locally for offline study
```

- يستعرض المستخدم المقررات العامة المنشورة من خلال استعلام مباشر وسريع عبر PostgREST لقراءة `LibraryCourse`, `CourseVersion`, والتصنيفات `ClassificationTaxonomy`.
- عند اختيار المقرر وتبنيه (`Version Adoption`)، يُنشئ الخادم سجل `WorkspaceCourseReference` يثبت الإصدار المحدد للمستخدم (`Pinned Version`).
- يسترجع التطبيق ملف المانيفست المجمع `manifest.json` من `Object Storage` ويقوم بحفظ البنية والمحتوى المشترك محليًا داخل Drift، مما يتيح للطالب دراسته واستعراضه بالكامل دون اتصال.

### رابعاً: مسار المقترحات والمراجعة والترقية (Collaborative Review & Version Promotion)

```text
[Author Client]         [Review Orchestrator]        [Reviewer Client]       [PostgreSQL Core]
       │                 (Edge Functions)                    │                       │
       │── 1. Submit ───────────►│                                                   │
       │   Proposal              │── 2. Freeze Content & Transition State ──────────►│
       │                         │                                                   │
       │                         │── 3. Dispatch Review Invitations ────────────────►│
       │                         │      (Candidate Accounts)                         │
       │                         │                                                   │
       │                         │                           │◄── 4. Accept & Fetch ─│
       │                         │                           │── 5. Submit Vote ────►│
       │                         │                                                   │
       │                         │── 6. Check Consensus & Quorum ───────────────────►│
       │                         │                                                   │
       │                   [If Approved]:                                            │
       │                         │── 7. Execute Version Promotion Transaction ──────►│
       │                         │      - Create SharedContentItems                  │
       │                         │      - Build VersionUnit/Lesson/ManifestItems     │
       │                         │      - Upload compiled manifest.json              │
       │                         │      - Publish CourseVersion (Immutable)          │
       │                         │      - Set Current Version & Add Attributions     │
       │                         │      - Deferred Purge of Workspace Drafts         │
       │◄── 8. Notify Outcome ───│◄──────────────────────────│                       │
```

1. **الرفع والتجميد:** يرفع المؤلف مقترح التحديث (`UpdateProposal`) عبر خدمة الـ Orchestrator؛ تُجمد بيانات التغيير فورًا لمنع أي تعديل لاحق.
2. **إدارة المراجعة:** تتولى خدمة المراجعة ترشيح مراجعين مؤهلين عشوائيًا، وتوليد دعوات المراجعة `ReviewInvitation`، وتتبع قراراتهم عبر `ReviewerAssignment` في بيئة معزولة تمامًا تمنع معرفة المراجعين لبعضهم أو معرفة المؤلف لهم.
3. **الاعتماد وتوليد الإصدار (Promotion Transaction):**
   - بمجرد تحقيق شروط القبول، تنفذ خدمة الـ Orchestrator معاملة موحدة:
     - نقل الملفات الجديدة والمعدلة لتصبح أصولاً مشتركة في `SharedContentItem`.
     - إنشاء السجلات الهيكلية للإصدار (`VersionUnit`, `VersionLesson`, `VersionManifestItem`).
     - تجميع وضغط ملف البنية الكاملة `manifest.json` ورفعه إلى مسار الإصدارات الثابت في Storage.
     - نشر السجل النهائي لـ `CourseVersion` وتحديث مؤشر `LibraryCourse.current_version_id`.
     - توثيق أسماء المساهمين والمراجعين في `CourseAttribution`.
     - تطهير مسودات التجاوز السحابية الخاصة بالمؤلف بعد أن أصبحت أصولاً معتمدة في المكتبة.

## 6. المعمارية الخاصة بـ Local-First والمزامنة (Local-First Architecture)

تعتمد معمارية النظام على جعل العميل مستقلاً وفعالاً دون الاعتماد الدائم على الاتصال الشبكي:

1. **مركزية Drift في العميل:**
   - تطبيق Flutter لا يعتمد على الذاكرة العشوائية المؤقتة؛ بل يمتلك قاعدة بيانات علائقية محلية كاملة عبر Drift.
   - البنية التعليمية (الوحدات، الدروس، البطاقات، الاختبارات) تُخزن وتُدار محليًا، وتعمل خوارزميات التكرار المتباعد ودراسة المحتوى محليًا 100%.
2. **اشتقاق حالة المزامنة (Zero Server-Side Write Amplification):**
   - لا يخزن الخادم حالة المزامنة `sync_status`؛ بل يحتفظ فقط بـ `pinned_version_id`.
   - يقوم تطبيق Flutter بمقارنة `pinned_version_id` المسجل محليًا مع `current_version_id` القادم من فهرس المكتبة العامة:
     - إذا تطابقا: الحالة `UP_TO_DATE`.
     - إذا اختلفا: الحالة `UPDATE_AVAILABLE`، ويظهر إشعار غير مزعج للمستخدم يتيح له الترقية باختياره.
3. **استقلال النسخ الخاصة والتعديلات المحلية:**
   - تعديل الطالب لبطاقة أو ملخص داخل درس مستورد من المكتبة العامة لا يطلب إذنًا من الخادم فورًا؛ بل يُسجل محليًا كـ `Private Copy`.
   - عند توفر الإنترنت، ترفع التعديلات إلى كيان `WorkspaceContentItem` السحابي كطبقة تجاوز للمقرر المرجعي لضمان الحفظ الاحتياطي فقط.

## 7. مواضع فرض الأمن والتحقق (Security Enforcement Architecture)

تُفرض متطلبات وثيقة `Data Access & Security Model` على مستويات معمارية متعددة تمنع أي ثغرة للوصول غير المصرح به:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Security Enforcement Points                     │
├────────────────────────┬───────────────────────────────────────────────┤
│ Enforcer               │ Responsibility & Scope                        │
├────────────────────────┼───────────────────────────────────────────────┤
│ PostgreSQL (RLS)       │ - عزل بيانات مساحات العمل والحسابات عزلاً تاماً. │
│                        │ - التحقق من سلسلة الملكية حتى الـ Identity.   │
│                        │ - فتح القراءة العامة لكيانات المكتبة المعتمدة.│
│                        │ - حظر التعديل أو الحذف لكيانات الإصدارات.     │
├────────────────────────┼───────────────────────────────────────────────┤
│ Storage Security Rules │ - ربط رفع الملفات بالملكية الشرعية للسجل.     │
│                        │ - حماية مسارات المسودات ومنع القراءة العامة لها.│
│                        │ - إتاحة مسارات الملفات المشتركة للقراءة العامة.│
├────────────────────────┼───────────────────────────────────────────────┤
│ Edge Functions Checks  │ - منع المراجعة الذاتية (Self-Review Check).    │
│                        │ - حجب هويات المراجعين أثناء مرحلة التحكيم.    │
│                        │ - حصر صلاحية إنشاء ونشر الإصدارات بالنظام فقط. │
└────────────────────────┴───────────────────────────────────────────────┘
```

1. **أمن قاعدة البيانات (Database Row Level Security):**
   تعتبر الـ RLS هي الحارس الأساسي؛ كل استعلام صادر عن `supabase_flutter` يفحص الـ JWT المرفق ويتحقق من أن العمليات على مساحات العمل والمحتوى الخاص لا تتجاوز حدود الحساب المالك (`account_id = current_account`).
2. **أمن ملفات التخزين (Storage Object Security):**
   تُقسم مجلدات التخزين إلى سياقات واضحة:
   - مسار عام ومحمي ضد الكتابة المباشرة للأصول المشتركة (`/shared/*`).
   - مسارات معزولة خاصة بمساحات العمل ومحمية بسياسات وصول تطابق ملكية السجل (`/workspaces/{workspace_id}/*`).
   - مسارات مؤقتة للمقترحات قيد التحكيم (`/proposals/{proposal_id}/*`).
   - مسار حزم المانيفست المجمعة للإصدارات (`/manifests/{version_id}/*`).
3. **ضمانات الخدمات السحابية (Orchestration Invariants):**
   تتولى الـ Edge Functions فرض الضوابط المعقدة التي يصعب التعبير عنها في RLS منفردة، مثل منع تضارب المصالح (حظر إرسال دعوة تحكيم لمؤلف المقترح أو لأي حساب آخر يشترك معه في نفس الـ `Identity`).

## 8. القرارات المعمارية والنقاط المؤجلة (Architectural Decisions & Deferred Items)

### أولاً: القرارات المعمارية المحسومة في هذه المرحلة:
1. **اعتماد PostgREST للعمليات القياسية:** استخدام واجهات PostgREST القياسية لعمليات القراءة والكتابة للبيانات الخاصة والمكتبة العامة، وتفادي كتابة Custom APIs إلا للعمليات المعقدة، للاستفادة الكاملة من كفاءة وسرعة RLS في Supabase.
2. **حصر العمليات الإجرائية المعقدة في Edge Functions:** قصر استخدام الـ Edge Functions على مسارات المراجعة، وتعيين المراجعين، واعتماد وترقية الإصدارات، وبناء ملف المانيفست.
3. **اعتماد نمط المانيفست المجمع للإصدارات:** توليد ملف `manifest.json` شامل لكل إصدار معتمد في Object Storage، مما يتيح لتطبيق Flutter تنزيل هيكل المقرر بالكامل في طلب واحد وحفظه في Drift وتفادي مئات الاستعلامات الشبكية الفردية.
4. **العزل الكامل للحساب النشط:** اعتماد فحص سياق الحساب النشط (`Student` مقابل `Teacher`) عند معالجة طلبات المزامنة لمنع اختلاط مساحات العمل لنفس الهوية.

### ثانياً: النقاط المؤجلة لمراحل التنفيذ اللاحقة (Implementation Phase):
1. **التفاصيل البرمجية لسياسات RLS والـ Storage:** كتابة الجمل البرمجية الفعلية لـ SQL RLS وسياسات Supabase Storage (مؤجل لـ Phase 9 Part 2 / Root #2).
2. **المنطق الرياضي لمعادلات النصاب (Quorum Formula Logic):** النسب المئوية الدقيقة لاعتماد التحديثات وتوزيع الأصوات داخل كود الـ Edge Functions.
3. **مواصفات حزم التسليم (Handoff Artifacts):** التوثيق الخاص بتسليم بيئة التطوير والتهيئة للمرحلة التنفيذية (موضوع Issue #22 المستقلة).
