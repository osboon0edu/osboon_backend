# قواعد إدارة العمل والتوثيق في مشروع عصبون | osboon

## 1. الهدف

هذه الوثيقة هي المرجع العام لتنظيم دورة العمل في المستودع، خصوصًا خلال مرحلة التوثيق وقبل بدء بناء الـBackend.

الهدف هو الحفاظ على:
- وضوح نطاق كل مهمة.
- ترتيب التنفيذ وفق Dependencies.
- Traceability بين القرار والتوثيق والـIssue والـPull Request.
- منع العمل المتداخل أو غير المحدد.
- منع الدوران في حلقات عمل غير منتجة.

## 2. اللغة المعتمدة

العربية هي اللغة الرسمية في:
- Documentation.
- Issues.
- Pull Requests.
- القرارات والتوضيحات المرتبطة بالمشروع.

تُستخدم الإنجليزية فقط عندما تكون جزءًا من مصطلح تقني أو اسم أداة أو ملف أو API أو مفهوم تقني يصعب استبداله دون فقدان الدقة.

## 3. Hierarchy الخاصة بالـIssues

نعتمد بنية هرمية للعمل:

```text
Root Issue
├── Parent Issue
│   ├── Child Issue
│   └── Child Issue
└── Parent Issue
    ├── Child Issue
    └── Child Issue
```

### Root Issue

تمثل المرحلة أو المبادرة الكبرى، وتحتوي على:
- الهدف العام.
- نطاق المرحلة.
- Execution Order.
- Dependencies.
- نقطة الانتقال إلى المرحلة التالية.
- Definition of Done الخاصة بالمرحلة.

### Parent Issue

تمثل نطاقًا منطقيًا داخل الـRoot Issue، ويمكن أن تحتوي على Child Issues.

### Child Issue

تمثل وحدة عمل محددة وقابلة للتنفيذ والمراجعة بشكل مستقل.

لا ننشئ Issues متشتتة خارج شجرة المشروع. إذا ظهر عمل جديد، يجب أولًا تحديد Parent المناسب له أو إنشاء Parent عند الحاجة.

## 4. مصدر الحقيقة

هناك فصل واضح بين نوعين من المعلومات:

### Execution Plan

يُوثق في الـRoot Issue، ويحدد:
- ترتيب التنفيذ.
- Dependencies.
- ما يمكن تنفيذه بالتوازي.
- ما يجب أن ينتظر.
- نقطة الانتقال بين المراحل.
- المراحل القادمة حتى لو لم تُنشأ Issues الخاصة بها بعد.

### Workflow Rules

تُوثق في هذه الوثيقة، وتحدد:
- كيف ننشئ وننفذ ونراجع ونغلق Issues.
- Branch Strategy.
- Pull Request Workflow.
- Scope Discipline.
- Definition of Done العامة.
- قاعدة إنشاء الـIssues تدريجيًا.

لا نكرر Execution Plan داخل هذه الوثيقة.

## 5. Progressive Issue Creation — إنشاء الـIssues تدريجيًا

نعتمد أسلوبًا تدريجيًا في إنشاء الـIssues، بحيث تكون صورة التنفيذ كاملة من البداية دون إنشاء أعمال مستقبلية قبل وقتها.

### القاعدة

**الـRoot Issue تثبت Execution Order والـPhases منذ البداية، لكن لا يعني وجود Phase في الـRoot أن الـIssue الخاصة بها قد أُنشئت.**

يُطبق ذلك كالتالي:

1. نحدد في الـRoot Issue المراحل وترتيبها وDependencies بينها.
2. ننشئ فقط الـIssue الخاصة بالمرحلة الحالية الجاهزة للتنفيذ.
3. لا ننشئ الـIssue الخاصة بالمرحلة التالية مسبقًا.
4. بعد اكتمال المرحلة الحالية وفق Definition of Done ودمج تغييراتها وإغلاق الـIssue الخاصة بها، ننشئ الـIssue التالية.
5. بعد إنشاء الـIssue التالية، نحدّث الـRoot Issue فورًا بإضافة رقم الـIssue ورابطها ومعلوماتها التنفيذية.
6. نكرر الدورة نفسها حتى نهاية المرحلة الكبرى.

مثال:

```text
Root Issue
│
├── Phase 1
│   └── Issue #2
│       ↓
│     Merge + Close
│
├── Phase 2
│   └── بعد اكتمال Phase 1:
│       إنشاء Issue الخاصة بـTerminology
│       ثم تثبيت رقمها ورابطها في Root Issue
│       ↓
│     Merge + Close
│
├── Phase 3
│   └── بعد اكتمال Phase 2:
│       إنشاء Issue الخاصة بـDomain Boundaries
│       ثم تثبيت رقمها ورابطها في Root Issue
│
└── ...
```

### لماذا نعتمد هذا الأسلوب؟

- يحافظ على وجود Execution Plan واضح منذ البداية.
- يمنع تضخم الـIssues المفتوحة قبل الحاجة إليها.
- يجعل كل Issue تمثل عملًا جاهزًا للتنفيذ.
- يحافظ على التدرج بين المراحل.
- يضمن أن الـRoot Issue تظل محدثة كخريطة تنفيذية للمشروع.

وجود Phase مستقبلية في الـRoot Issue لا يتطلب إنشاء Issue لها، بل يكفي توثيق أن Issue الخاصة بها ستُنشأ عند اكتمال الـPhase السابقة.

## 6. Branch Strategy

كل Issue قابلة للتنفيذ يجب أن تعمل على Branch مستقل.

صيغة التسمية:

```text
<type>/issue-<number>-<short-name>
```

أمثلة:

```text
docs/issue-02-project-management
docs/issue-09-terminology
docs/issue-12-domain-boundaries
```

### قاعدة إنشاء الـBranch

يُنشأ الـBranch من آخر تحديث في `main`.

قبل البدء:
1. التأكد من أن `main` يحتوي على آخر التغييرات.
2. إنشاء Branch مستقل للـIssue.
3. عدم تنفيذ التغييرات مباشرة على `main`.

### قاعدة أساسية

**ممنوع العمل مباشرة على `main` في هذه المرحلة.**

## 7. Scope Discipline

كل Issue لها Scope واضح.

يجب ألا تحتوي التغييرات على أعمال جانبية لا تتطلبها الـIssue.

إذا اكتشفنا أثناء التنفيذ شيئًا خارج Scope:

1. نتوقف عن إدخاله في التغيير الحالي.
2. نحدد الـIssue المناسبة له.
3. إذا لم توجد، ننشئ Child Issue جديدة تحت الـParent المناسب.
4. نضيف Dependency عند الحاجة.
5. نحدث Execution Order في الـRoot Issue إذا تغير ترتيب التنفيذ.

الهدف هو أن يكون كل تغيير قابلًا للإجابة عن السؤال:

> لماذا تم إجراء هذا التغيير؟

والإجابة يجب أن تعود إلى Issue محددة.

## 8. Issue → Branch → Pull Request → Merge → Closure

دورة العمل القياسية:

```text
Issue
  ↓
Branch
  ↓
Changes
  ↓
Pull Request
  ↓
Review
  ↓
Merge
  ↓
Issue Closure
```

### القاعدة

إغلاق الـIssue ليس بديلًا عن دمج التغيير.

الـIssue تُغلق بعد:
- اكتمال التغييرات المطلوبة.
- مراجعة الـPull Request.
- دمج الـPull Request في `main`.
- التأكد من أن التوثيق أو الحالة الناتجة متوافقة مع Acceptance Criteria.

## 9. Pull Request

كل Pull Request يجب أن:
- يكون مرتبطًا بـIssue محددة.
- يشرح باختصار ما تم تغييره.
- يوضح أي قرارات مهمة.
- يلتزم بـScope الـIssue.
- يكون قابلًا للمراجعة دون الحاجة إلى تخمين سبب التغيير.

يفضل أن يكون Pull Request صغيرًا ومركزًا قدر الإمكان.

## 10. Dependencies

عند وجود Dependency بين Issues:
- يجب توثيقها صراحة.
- لا تبدأ Issue تعتمد على نتيجة غير مكتملة من Issue أخرى.
- يمكن تنفيذ Issues بالتوازي فقط إذا لم تتعارض مخرجاتها ولم تعتمد إحداها على الأخرى.

في نمط التنفيذ التدريجي، تكون المرحلة التالية عادةً معتمدة على اكتمال المرحلة السابقة، لذلك لا تُنشأ Issue التالية قبل تحقق الـDependency الأساسية.

إذا تغيرت Dependency أثناء التنفيذ، يجب تحديث الـRoot Issue.

## 11. Definition of Done

تُعتبر Issue مكتملة عندما:
- تحققت Acceptance Criteria.
- لم يتم إدخال تغييرات خارج Scope دون Issue مناسبة.
- تم فتح Pull Request.
- تمت المراجعة.
- تم الدمج في `main`.
- تم تحديث أي توثيق متأثر.
- تم إغلاق الـIssue.
- تم تحديث الـRoot Issue إذا كان إغلاقها يسمح بالانتقال إلى Phase التالية أو يتطلب تثبيت Issue جديدة.

## 12. التوثيق كمنتج قابل للمراجعة

التوثيق ليس ملاحظات مؤقتة.

كل وثيقة يجب أن تكون:
- واضحة.
- قابلة للمراجعة.
- مرتبطة بالـIssue التي أنشأتها أو عدلتها.
- متسقة مع بقية الوثائق.
- خالية من القرارات الضمنية غير الموثقة.

عند وجود تعارض بين وثيقتين، يجب إنشاء أو تحديث Issue لمعالجة التعارض بدل اختيار أحدهما بشكل صامت.

## 13. الانتقال بين المراحل

لا ننتقل إلى مرحلة جديدة لمجرد أن هناك رغبة في البدء بها.

الانتقال يعتمد على Definition of Done للمرحلة السابقة.

عند اكتمال المرحلة الحالية:
1. نتأكد من إغلاق الـIssue الخاصة بها.
2. ننشئ الـIssue الخاصة بالمرحلة التالية.
3. نثبت رقمها ورابطها في الـRoot Issue.
4. تصبح هي الـIssue النشطة التالية في Execution Order.

بالنسبة لمرحلة التوثيق الحالية، يجب الوصول إلى حالة تسمح بالانتقال إلى **Logical Data Model** دون وجود غموض جوهري في:
- Terminology.
- Domain Boundaries.
- States & Workflows.
- Entity / Relationship Classification.

بعد اعتماد الـLogical Data Model يمكن الانتقال لاحقًا إلى تصميم وتنفيذ الـBackend باستخدام **Supabase**.

## 14. قاعدة التغيير

أي تغيير في قواعد العمل نفسها يجب أن يكون موثقًا وقابلًا للتتبع، ولا يتم إدخال قاعدة جديدة بشكل ضمني أثناء تنفيذ Issue أخرى.

عند الحاجة إلى تغيير هذه القواعد:
1. نفتح Issue مناسبة.
2. ننفذ التغيير على Branch مستقل.
3. نراجع Pull Request.
4. ندمج التغيير.
5. تصبح النسخة المدمجة هي المرجع الجديد.
