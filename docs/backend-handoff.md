# وثيقة تسليم المنظومة الخلفية | Backend Handoff — مشروع عصبون (osboon)

## 1. مدخل والهدف من وثيقة التسليم (Introduction & Objective)

تمثل هذه الوثيقة المخرج النهائي لـ **Phase 9 — Backend Architecture & Handoff** (عبر Child Issue #22) وخاتمة أعمال **Root Issue #1 — تأسيس مرحلة التوثيق وإدارة العمل قبل بناء الـBackend**.

تهدف الوثيقة إلى وضع **ميثاق تسليم رسمي وملزم (Binding Handoff Agreement)** ينقل المشروع من مرحلة التصميم والتوثيق المرجعي إلى مرحلة التنفيذ الفعلي في **Root #2 — تأسيس الـSupabase Backend (Backend Foundation)**.

تحدد هذه الوثيقة:
- الحزمة المرجعية المعتمدة للمشروع ومكانتها الحاكمة.
- القرارات المعمارية والثوابت المحسومة التي **يُحظر قطعيًا إعادة تصميمها** أثناء التنفيذ في Root #2 دون قرار موثق جديد.
- النطاق الدقيق لمسؤوليات Root #2 مقارنة بنطاقات المراحل اللاحقة (Root #3 وما بعدها) لمنع تشتت Scope.
- المتطلبات الهندسية والقواعد التشغيلية المعتمدة لإدارة وتطوير الـBackend عبر GitHub CI/CD وSupabase.
- شروط الجاهزية والمدخلات المطلوبة لبدء العمل في Root #2.

## 3. القرارات المعمارية والثوابت المحسومة (Non-Negotiable Invariants)

يستلم منفذ **Root #2** القرارات المعمارية التالية كـ **ثوابت هندسية قطعية ومغلقة (Non-Negotiable Invariants)**؛ ويُمنع فتح النقاش حولها أو محاولة إعادة هندستها ضمن مسار العمل الاعتيادي:

1. **معمارية Local-First وتكامل Drift مع Supabase:**
   - تطبيق Flutter هو تطبيق **Local-First** يعتمد على **Drift** لقراءة ودراسة وتعديل المحتوى محليًا دون اشتراط الاتصال بالإنترنت.
   - كيانات `Workspace*` على خادم Supabase تمثل **طبقة مزامنة سحابية خاصة (Cloud Sync Overlay)** وليست مستودعًا إجباريًا للتشغيل اللحظي.
2. **فصل الهوية عن الحسابات الوظيفية (Persona Decoupling):**
   - هوية الدخول (`Identity`) الموثقة عبر Supabase Auth منفصلة مفاهيميًا ووظيفيًا عن الحساب (`Account`).
   - يمكن للـ `Identity` الواحدة امتلاك `StudentAccount` و `TeacherAccount`، وتُفصل مساحات العمل والصلاحيات لكل سياق ولا تختلط بينهما.
3. **طبيعة الإصدارات المعتمدة وثباتها (Immutable Course Versions):**
   - السجلات التابعة للإصدار المنشور (`CourseVersion`, `VersionUnit`, `VersionLesson`, `VersionManifestItem`, `SharedContentItem`) غير قابلة للتعديل أو الحذف نهائيًا (`Immutable`).
4. **إدارة الإصدارات على مستوى الملفات المتغيرة (File-Level Versioning):**
   - لا يتم استنساخ المادة التعليمية كاملة عند كل إصدار؛ بل يعاد استخدام مراجع الملفات غير المتغيرة عبر `SharedContentItem`، وتُسجل فقط الإشارات للملفات المتغيرة (`Changed Content`).
5. **اشتقاق حالة المزامنة لدى العميل (Zero Server-Side Write Amplification):**
   - لا يحتوي جدول `WorkspaceCourseReference` على حقل لحالة المزامنة؛ بل تشتق الحالة (`UP_TO_DATE` أو `UPDATE_AVAILABLE`) محليًا في تطبيق Flutter بمقارنة `pinned_version_id` مع `LibraryCourse.current_version_id`.
6. **فصل التخزين المجمع عن البيانات الوصفية (Compiled Manifest Pattern):**
   - كل إصدار معتمد يمتلك ملف مانيفست مجمع ومضغوط `manifest.json` يُرفع في Supabase Storage (`manifest_storage_path`) لتمكين العميل من تنزيل هيكل المقرر بالكامل في طلب شبكي واحد.
7. **المنع المبدئي والعزل التام للمستأجر (Deny by Default & Tenant Isolation):**
   - تُعامل كل مساحة عمل كبيئة خاصة معزولة كليًا؛ ولا يتم الوصول للبيانات إلا بإثبات صريح لسلسلة الملكية تبدأ من الـ `Identity` وتمر بالـ `Account` المالك لمساحة العمل.
8. **حظر المراجعة الذاتية وعزل المراجعين (Review Guardrails):**
   - حظر مراجعة المستخدم لمقترح أنشأه هو أو أي حساب يتبع لنفس هويته (`author_account_id != reviewer_account_id`).
   - حجب هويات المراجعين وقراراتهم أثناء مرحلة المراجعة النشطة (`UNDER_REVIEW`) لضمان العدالة وعدم التأثير المتبادل.

## 4. المبادئ الهندسية الملزمة لإدارة الـBackend (Mandatory Engineering Constraints)

بناءً على وثيقة `backend-engineering-principles.md` المعتمدة، يجب على **Root #2** الالتزام بالمبادئ الهندسية التشغيلية التالية:

### 4.1 مستودع Git هو مصدر الحقيقة الأوحد (Git as Source of Truth)
- **قاعدة البيانات السحابية (Supabase Cloud) هي Deployment Target وليست Source of Truth.**
- كافة تعريفات قاعدة البيانات (Tables, Types, Extensions, Functions, Policies) تُدار كملفات نصية برمجية مصرحة (Declarative Schemas) داخل المستودع.
- أي تعديل يدوي مباشر على لوحة تحكم Supabase السحابية (Supabase Dashboard) في بيئات Staging أو Production يُعتبر خرقًا هندسيًا محظورًا.

### 4.2 حظر بيئة الـBackend المحلية المستمرة (No Persistent Local Backend DB)
- لا يدير المشروع قاعدة بيانات سحابية أو حاوية Docker محلية دائمة ومستمرة في جهاز المطور للـBackend.
- تعتمد الدورة الهندسية على أدوات التحقق الآلي في بيئة CI (عبر إنشاء قاعدة بيانات مؤقتة Ephemeral داخل الـRunner واختبارها ثم إتلافها فورًا).

### 4.3 إدارة دورة حياة قاعدة البيانات عبر GitHub CI/CD المؤتمت
- تمر كافة عمليات التحقق، والـ Linting، واختبارات قاعدة البيانات، وتوليد الـ Migrations، والنشر إلى البيئات السحابية عبر **GitHub Actions**.

### 4.4 إدارة البيئات وفصل الأسرار (Environment & Secrets Management)
- تُدار بيئتا **Staging** و **Production** كبيئات تشغيل سحابية منفصلة في Supabase.
- تُحفظ مفاتيح الوصول والكلمات السرية ضمن **GitHub Secrets / Environments**، ويُحظر تمامًا تخزين أي بيانات سرية أو رموز وصول داخل المستودع البرمجي.

## 6. متطلبات الجاهزية والمدخلات المطلوبة لبدء Root #2 (Prerequisites & Entry Criteria)

قبل إطلاق أول Issue تنفيذية في Root #2، يجب التأكد من توفر المتطلبات التالية:

1. **جاهزية المستودع البرمجي (Git Baseline):**
   - اعتماد ودمج PR الخاص بوثيقة Handoff في فرع `main`.
   - تأسيس فرع التكامل `develop` ليكون مستقرًا ومطابقًا لـ `main`.
2. **إصدار بيئة العمل وأدوات Supabase:**
   - اعتماد الإصدار الرسمي لـ **Supabase CLI** (الإصدار المرجعي الموصى به: `v2.117.x` فما فوق).
3. **تهيئة البيئات السحابية على Supabase Cloud:**
   - توفر مشروع Supabase سحابي مخصص لبيئة **Staging**.
   - توفر مشروع Supabase سحابي مخصص لبيئة **Production**.
4. **تهيئة إعدادات GitHub Secrets & Environments:**
   - إعداد بيئتي GitHub Environment: `staging` و `production`.
   - تسجيل الرموز السرية التالية في المستودع:
     - `SUPABASE_ACCESS_TOKEN` (Repository Secret)
     - `STAGING_PROJECT_ID` و `STAGING_DB_PASSWORD` (Staging Environment Secrets)
     - `PRODUCTION_PROJECT_ID` و `PRODUCTION_DB_PASSWORD` (Production Environment Secrets)
